# Типичные проблемы агентных систем и как TaskPilot их решает

Сводка рисков, характерных для агентных фреймворков, и того, как наш фреймворк их учитывает или закрывает.

---

## 1) Prompt-injection и «угон агента» через контент

**Проблема:** Агент читает внешние тексты (страницы, письма, сообщения, skills) и начинает выполнять вредные инструкции. Даже «закалённые» конфиги в тестах часто уводят в сторону.

**Решения (общие):**
- **Tools firewall** — строгая политика, какие tools можно вызывать в каком контексте (allowlist).
- Выходные форматы только по **JSON schema + server-side validation**.
- **Разделение контекстов:** «untrusted content» хранить отдельно и **никогда** не давать как system/инструкцию.
- Непрерывный security testing и редтиминг (не разовая настройка).

**В TaskPilot:**
- **AccessPolicy** — allowlist инструментов: `allowedTools`, `deniedTools`, `guard`. Нет политики — по умолчанию все инструменты доступны; задал политику — только разрешённые и прошедшие guard.
- **Разделение контекстов:** system prompt и цель задаются вызывающим кодом. Рекомендация: непроверенный контент передавать **только в user message** (например, отдельным блоком «Внешний контент: …»), никогда не подмешивать в system. Долгосрочную память изолировать по `principal.id` (ScopedLongTermMemory), чтобы в контекст не попадали чужие данные.
- **Валидация вывода** — фреймворк не парсит final answer за тебя. Решение: на стороне приложения — контракт (JSON schema) и валидация ответа перед использованием; при использовании tool calling ответ модели структурирован провайдером (OpenAI и т.д.).

## 2) Skills/плагины как supply-chain: вредоносные «скиллы»

**Проблема:** Marketplace скиллов становится каналом доставки малвари/утечек (особенно если скилл может запускать команды/читать файлы).

**Решения (общие):**
- В проде: только **curated registry** (подписи, ревью, version pinning).
- Сканер skills перед установкой + запрет «скачать и исполнить удалённое».
- **Песочница:** по умолчанию без доступа к ФС/SSH/секретам.

**В TaskPilot:**
- **Нет marketplace.** Инструменты регистрируются в коде приложения (`ToolRegistry.register(...)`). Цепочка поставок — твой репозиторий и деплой; только то, что ты явно подключил.
- Песочница и доступ к ФС/сети — на стороне процесса (контейнер, права пользователя, секреты через env/vault). Фреймворк не выполняет произвольный код извне; каждый tool — твоя реализация.

---

## 3) Экспонированный gateway/control plane в интернет

**Проблема:** Пользователи поднимают агент-шлюз наружу без защиты → утечки/захват.

**Решения (общие):**
- По умолчанию bind только на **localhost**.
- Обязательная **authN/authZ**, IP allowlist, mTLS/VPN.
- Отдельные сервис-аккаунты, строгие секреты (vault), аудит и алерты.

**В TaskPilot:**
- **Нет своего gateway.** TaskPilot — библиотека, встраиваемая в твой backend. Сетевой экспоз — ответственность приложения: твой HTTP API, твой bind (localhost/0.0.0.0), твоя authN/authZ перед вызовом `runAgentLoop`. Рекомендация: перед созданием `accessContext` — аутентификация и проверка прав; секреты (API keys) — из env/vault, не из кода.

## 4) Приватность: путаница медиа/файлов и утечки

**Проблема:** В агентных системах часто всплывают баги «не тот файл / не тому пользователю» (чаты, медиа). Это типичный класс инцидентов privacy breach.

**Решения (общие):**
- Жёсткая **tenant-изоляция** на сервере (owner/workspace checks в каждом запросе).
- **Signed URLs** для медиа, короткий TTL, доступ только после auth.
- **Audit log** на каждое чтение/выдачу файла.

**В TaskPilot:**
- **Principal** и **tenantId** передаются в каждый вызов инструмента (`context.principal`). Инструменты, работающие с файлами/медиа, должны проверять `context.principal.id` и `tenantId` и выдавать только «свои» ресурсы.
- **ScopedLongTermMemory** — изоляция по scope (principal.id), чтобы в контекст не попадали чужие записи.
- Signed URLs, TTL, audit log — реализуются в твоих инструментах и backend (при выдаче URL и при доступе к файлу).

## 5) Нестабильность сессий/контекста и «галлюцинации маршрута»

**Проблема:** Сессии рвутся, контекст теряется, агент ведёт себя непредсказуемо (в т.ч. потеря сессии после idle).

**Решения (общие):**
- Явная модель **run/session state** в БД.
- **Автосводка (summary)** + фиксированный window контекста.
- **Idempotent tools** — повторный вызов не выполняет действие второй раз.

**В TaskPilot:**
- **Состояние ранна** возвращается из `runAgentLoop` (`AgentRunState`: messages, finalAnswer, runId, principalId). Фреймворк сам не персистит его; приложение может сохранять в БД по `runId` и при необходимости восстанавливать контекст (например, последние N сообщений + summary).
- **Один ран = один буфер** (BufferMemory). Для «сессии» из нескольких шагов — твоя логика: хранить историю в БД, при следующем запросе подставлять summary или скользящее окно.
- **Idempotent tools** — рекомендация при проектировании инструментов: проверять, было ли действие уже выполнено (по idempotency key, по состоянию), и не дублировать побочные эффекты.

## 6) Непредсказуемость: direct API vs agent path

**Проблема:** Один и тот же запрос к модели по прямому API может отвечать корректно, а через агентный пайп — нет (шум промптов, лишние инструкции, tool traces).

**Решения (общие):**
- Минимизировать системный промпт, убрать «болтовню».
- Логировать **полный assembled prompt** (внутренне) и детерминировать настройки (temperature, top_p).
- **Контракт на вывод:** schema + проверки.

**В TaskPilot:**
- **System prompt** задаётся тобой (`options.systemPrompt`); можно держать его коротким и без лишних инструкций.
- Собранные сообщения доступны как `memory.getMessages()` до и после цикла; приложение может логировать их (без секретов) для отладки и редтиминга.
- **Параметры модели** (temperature, top_p) — в реализации `LLMAdapter` (например, в OpenAIAdapter при вызове API). Рекомендация: вынести в опции и по возможности фиксировать для воспроизводимости.
- Контракт на вывод — на стороне приложения: валидация final answer и tool results по своей schema.

## 7) Производительность и стоимость (оверхед агентных циклов)

**Проблема:** Агентный цикл может плодить лишние вызовы/процессы; в issues — запросы про daemon-mode, кеширование.

**Решения (общие):**
- **Кеш tool-результатов**, дедуп запросов.
- Один **долгоживущий воркер (daemon)** вместо spawn per request.
- **Лимиты** на шаги агента (max_steps) и бюджет токенов.

**В TaskPilot:**
- **maxSteps** — жёсткий лимит на число итераций цикла (`AgentLoopOptions.maxSteps`, по умолчанию 15). Превышение — цикл завершается.
- **Кеш tool-результатов** и дедуп — не встроены; реализуются в инструментах или в обёртке над `ToolRegistry.execute` (например, ключ по tool name + hash(args), TTL).
- **Один воркер** — архитектура приложения: один процесс/воркер обрабатывает запросы и вызывает `runAgentLoop`; фреймворк не порождает отдельные процессы.
- **Бюджет токенов** — не задаётся во фреймворке; при необходимости передавать в LLM-адаптер (max_tokens и т.п.) и/или считать токены на своей стороне и останавливать ран при превышении.

## Сводная таблица

| Проблема | Что есть в TaskPilot | Что делать на стороне приложения |
|----------|-------------------------|----------------------------------|
| 1. Prompt injection | AccessPolicy (allowlist, guard), разделение контекста (system vs user) | Untrusted только в user message; валидация вывода по schema |
| 2. Вредоносные skills | Нет marketplace, tools только из кода | Песочница процесса, ревью кода |
| 3. Экспоз gateway | Нет своего gateway | Bind, authN/authZ, секреты в vault |
| 4. Приватность/медиа | Principal, tenantId, ScopedLongTermMemory | Owner checks в tools, signed URLs, audit |
| 5. Нестабильность сессий | AgentRunState, один буфер на ран | Персистенция в БД, summary, idempotent tools |
| 6. Непредсказуемость вывода | Короткий system prompt, доступ к messages | Логирование промпта, temperature/top_p в адаптере, контракт на вывод |
| 7. Производительность/стоимость | maxSteps | Кеш tool-результатов, один воркер, лимит токенов в адаптере |
